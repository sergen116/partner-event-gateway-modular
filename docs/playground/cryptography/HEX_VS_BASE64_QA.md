# Hex vs Base64 — Why Each Encoding for Each Job

A focused explanation of two design choices in `HmacVerifier.java`:

1. **Why hex** is used for the stored secret hash
2. **Why base64** is used for the wire signature
3. A deep step-by-step walk-through of why hex is "diff-friendly" (the part
   that's easiest to wave past without really understanding)

Both encodings turn raw bytes into text. Neither is encryption. Neither
adds security. The choice is purely about **operational fit**: storage and
wire have different constraints.

---

## Part 1: Why **hex** for the stored secret hash

The DB stores `SHA-256(secret)` — 32 raw bytes. Those bytes contain
non-printable characters (`0x00`, `0x7f`, etc.), so they can't go in a
`VARCHAR` directly. We need a text encoding. Hex wins for **five
operational reasons**.

### 1. Convention — every standard tool emits hex

When a partner generates their key, the tools they reach for produce hex
by default:

```bash
$ echo -n "my-partner-secret" | sha256sum
b94d27b9934d3e08a52e52d7da7dabfac484efe37a5380ee9088f7ace2efcde9  -

$ echo -n "my-partner-secret" | openssl dgst -sha256
SHA2-256(stdin)= b94d27b9934d3e08a52e52d7da7dabfac484efe37a5380ee9088f7ace2efcde9
```

Both produce the **same 64-char hex string**. The partner pastes it into
onboarding; the gateway stores it verbatim. Zero conversion friction.

If we stored base64 instead, every partner would need to remember to
pipe through `xxd -r -p | base64` — a step easy to forget.

### 2. Fixed width — perfect for `CHAR(64)`

SHA-256 always produces exactly 32 bytes:

| Encoding | Output for 32 bytes | Column type |
|---|---|---|
| Hex | **always** 64 chars | `CHAR(64)` ✅ |
| Base64 | 44 chars **including `=` padding** | `CHAR(44)` works but the `=` is awkward |

`CHAR(64)` lets the DB enforce the length at the schema level. Any row
with a different length is corrupt by definition — you catch bugs at
insert time, not at signature-verification time.

### 3. Case-insensitive — survives log normalization

Hex only uses `0-9 a-f`. These two strings represent the **same bytes**:

```
b94d27b9934d3e08...
B94D27B9934D3E08...
```

Logging pipelines, ticketing systems, and copy-paste sometimes change
case. Hex doesn't care. Base64 *does* — `A` and `a` are different bytes:

```
Base64: "QQ==" → 0x41 ('A')
Base64: "YQ==" → 0x61 ('a')
```

A case-folded base64 string silently decodes to garbage.

### 4. Diff-friendly — humans can spot changes

Each byte is exactly **2 hex chars**, and the boundary never moves. If
two hashes differ in one byte, you see it instantly. (Full step-by-step
in Part 3.)

### 5. URL-safe and shell-safe

Hex uses only `[0-9a-f]`. No special characters anywhere. You can:

- put it in a URL without encoding
- pass it as a CLI argument without quoting
- grep for it without escaping
- paste it into a JSON value without worrying

Base64 uses `+`, `/`, and `=`, which break in URLs (`+` becomes space,
`/` is a path separator, `=` triggers query-string parsing). That's why
a separate `base64url` variant exists — extra complication.

### Code reference

```java
// Partner.secretHashHex() returns a 64-char hex string
byte[] keyBytes = HexFormat.of().parseHex(secretHashHex);
// keyBytes is the same 32 raw bytes that came out of SHA-256
```

`parseHex` is purely text→bytes. No crypto. The hex form was chosen so
this single line handles loading the key.

## Part 2: Why **base64** for the wire signature

The signature on the wire (`X-Signature` HTTP header) has *different*
constraints — it's transient, machine-only, and bandwidth-sensitive.

### 1. Compactness — every byte counts on the wire

Same 32-byte HMAC tag, two encodings:

```
Hex (64 chars):
  X-Signature: b94d27b9934d3e08a52e52d7da7dabfac484efe37a5380ee9088f7ace2efcde9

Base64 (44 chars):
  X-Signature: uU0nuZNNPgilLlLX2n2r+sSE7+N6U4DukIj3rOLvzek=
```

Base64 is **31% smaller** (44 vs 64 chars). Across millions of partner
requests per day, that's measurable bandwidth. Storage doesn't care about
20 bytes per row, but the wire does — every header is sent on every
request, often through narrow mobile uplinks.

**Why the size difference?** Math:

| Encoding | Bits per char | Chars for 32 bytes (256 bits) |
|---|---|---|
| Hex | 4 | 256 / 4 = **64** |
| Base64 | 6 | ceil(256 / 6) + padding = **44** |

Hex wastes half its alphabet — 16 characters out of 256 possible ASCII
chars. Base64 uses 64 chars and packs 50% more data per character.

### 2. Humans don't read it — readability doesn't matter

The stored hash gets read by ops engineers debugging issues. The wire
signature gets:

- generated by the partner's HTTP client (machine)
- transmitted over the wire (machine)
- decoded and compared by the gateway (machine)
- discarded after one request (lifetime ~ms)

No human ever needs to eyeball it. The diff-friendliness advantage of
hex evaporates because nobody is diffing.

### 3. HTTP headers must be ASCII — base64 is built for this

You can't put raw bytes in an HTTP header — bytes like `0x00`, `0x0d`,
`0x0a` would corrupt the protocol (HTTP uses CRLF as delimiter). You
need *some* text encoding.

Base64 was literally designed for this in MIME/email. It's the default in:

- HTTP Basic Auth (`Authorization: Basic <base64>`)
- JWT signatures (`xxx.yyy.zzz` — each segment base64url)
- AWS Signature v4
- Stripe webhook signatures
- Slack request signatures

Partners writing client libraries reach for `Base64.getEncoder()`
instinctively. Going against this convention adds friction.

### 4. The padding `=` is fine in headers (unlike URLs)

The `=` padding character that makes base64 awkward in URLs is **fine in
HTTP header values**. Headers don't parse `=` specially. So the main
downside of base64 doesn't apply here.

### Code reference

```java
// HmacVerifier.matches(...)
byte[] presented = Base64.getDecoder().decode(presentedSignatureBase64);
// 'presented' is now 32 raw bytes, ready for constant-time compare
byte[] expected = hmacSha256(keyBytes, canonical);
return MessageDigest.isEqual(expected, presented);
```

One line of base64 decoding, then straight into bytes for comparison.

## Part 3: Why hex is "diff-friendly" — step by step

The claim: **if a single byte changes, hex shows you exactly where;
base64 hides it.** Let's build this up from scratch.

### Step 1: What "encoding bytes as text" actually means

A SHA-256 hash is **32 raw bytes**. Each byte is a number from 0 to 255.
Example:

```
Byte position:  0    1    2    3    ...   31
Raw bytes:     0xb9 0x4d 0x27 0xb9 ... 0xe9
```

We can't store raw bytes in a `VARCHAR` column or print them in logs
(many byte values are non-printable). So we convert them to text using
either **hex** or **base64**.

The key question: when one byte changes, **how many characters change in
the encoded string?**

### Step 2: How hex encodes bytes

Hex uses **2 characters per byte**, always. Each character represents
4 bits.

```
1 byte = 8 bits = 2 hex chars
```

Example:

```
Byte 0xb9  →  "b9"   (always 2 chars)
Byte 0x4d  →  "4d"   (always 2 chars)
Byte 0x27  →  "27"   (always 2 chars)
```

So 32 bytes encode to **exactly 64 hex chars**, and each pair of chars
maps to **exactly one byte**:

```
Position in string:   0  1  2  3  4  5  6  7  ...
Hex string:           b  9  4  d  2  7  b  9  ...
                      └──┘  └──┘  └──┘  └──┘
                       │     │     │     │
                      byte0 byte1 byte2 byte3
```

**The byte boundary in the string is always at even positions
(0, 2, 4, 6, ...).** It never moves.

### Step 3: What happens in hex when ONE byte changes

Suppose byte 31 (the last byte) changes from `0xe9` to `0x00`:

```
Original bytes:  ... 0x9088f7ac 0xe2efcd 0xe9
Modified bytes:  ... 0x9088f7ac 0xe2efcd 0x00
                                          ^^ this byte changed
```

In hex:

```
Original:  ...9088f7ace2efcde9
Modified:  ...9088f7ace2efcd00
                            ^^
```

**Only the last 2 characters changed.** Every other character is
identical, in the exact same position. Your eye jumps straight to the
difference.

### Step 4: How base64 encodes bytes (this is the key part)

Base64 uses **4 characters per 3 bytes**. It does not encode each byte
independently — it groups bytes into chunks of 3 and converts the entire
24-bit chunk into 4 characters of 6 bits each.

```
3 bytes = 24 bits = 4 base64 chars
```

Visualizing the bit layout:

```
Bytes:    [ byte 0 ][ byte 1 ][ byte 2 ]
Bits:     bbbbbbbb  bbbbbbbb  bbbbbbbb     (24 bits total)

Regrouped into 6-bit chunks:
          [bbbbbb][bbbbbb][bbbbbb][bbbbbb]   (4 base64 chars)
            char0   char1   char2   char3
```

**The byte boundaries do not align with the character boundaries.** Each
base64 character contains bits from up to 2 different bytes:

- `char0`: bits 0-5 of byte 0
- `char1`: bits 6-7 of byte 0 + bits 0-3 of byte 1   ← **spans two bytes**
- `char2`: bits 4-7 of byte 1 + bits 0-1 of byte 2   ← **spans two bytes**
- `char3`: bits 2-7 of byte 2

### Step 5: What happens in base64 when ONE byte changes

When you change one byte, you change up to 8 bits. Those 8 bits are
smeared across **multiple base64 characters** because of the 3-byte
grouping.

Concrete example. Take 3 bytes:

```
Original bytes: [0x4d, 0x61, 0x6e]   ("Man" in ASCII)
```

Base64 encoding step by step:

```
Bytes:    0x4d        0x61        0x6e
Binary:   01001101    01100001    01101110

Regroup into 6-bit chunks:
          010011  010110  000101  101110

Each 6-bit value mapped to base64 alphabet:
          010011 = 19 → 'T'
          010110 = 22 → 'W'
          000101 =  5 → 'F'
          101110 = 46 → 'u'

Result:   "TWFu"
```

Now change just **one bit** in the middle byte (`0x61` → `0x60`):

```
Bytes:    0x4d        0x60        0x6e
Binary:   01001101    01100000    01101110
                             ^ this bit changed

Regroup:  010011  010110  000001  101110
                          ^^^^^^ different chunk now

Mapping:  010011 → 'T'    (unchanged)
          010110 → 'W'    (unchanged)
          000001 → 'B'    (was 'F')
          101110 → 'u'    (unchanged)

Result:   "TWBu"
```

Notice: changing **1 bit in 1 byte** changed **1 character** in base64.
So far it sounds the same as hex. But watch what happens with a
realistic full-hash example.

### Step 6: The real problem — single-byte change in a full hash

**Hex comparison** (last byte changed from `0xe9` to `0x00`):

```
expected: b94d27b9934d3e08a52e52d7da7dabfac484efe37a5380ee9088f7ace2efcde9
got:      b94d27b9934d3e08a52e52d7da7dabfac484efe37a5380ee9088f7ace2efcd00
                                                                        ^^
```

Your eye scans left to right, sees identical chars, and lands on the
`00` at the end. **2 chars different, in 1 location, at a predictable
position.**

**Base64 comparison** (same byte change):

```
expected: uU0nuZNNPgilLlLX2n2r+sSE7+N6U4DukIj3rOLvzek=
got:      uU0nuZNNPgilLlLX2n2r+sSE7+N6U4DukIj3rOLvzgA=
                                                  ^^^
```

Now you see `zek=` became `zgA=`. Three characters changed: `e`→`g`,
`k`→`A`, and the byte change has rippled across the final group.

**Why?** The last byte of a 32-byte hash falls in an awkward position.
32 bytes = 10 full groups of 3 + 2 leftover bytes. Those leftover bytes
are encoded with padding (`=`), and changing one of them affects bits
across multiple base64 chars in the final group.

### Step 7: The core principle

| | Hex | Base64 |
|---|---|---|
| Bytes per "unit" | 1 byte = 1 unit | 3 bytes = 1 unit |
| Chars per unit | 2 | 4 |
| Byte boundaries align with char boundaries? | ✅ Always | ❌ No |
| Change 1 byte → chars affected | Always exactly 2, always in the same position | 1-4 chars, position depends on which byte |
| Mental model | "Each byte is a 2-char window, scan left to right" | "Bytes get scrambled across char groups" |

**Hex is like a ruler:** every byte has a fixed slot. Position 10-11 is
always byte 5. Always.

**Base64 is like a zipper:** bytes get interleaved across characters. To
find "which byte changed," you mentally have to ungroup, rebuild bits,
and figure out the boundaries.

### Step 8: Why this matters at 2am in production

You're debugging why a partner's signatures stopped verifying. You have
two hashes side by side in a log:

**Hex** (in a log line):
```
expected key fingerprint: b94d27b9934d3e08a52e52d7da7dabfac484efe37a5380ee9088f7ace2efcde9
got key fingerprint:      b84d27b9934d3e08a52e52d7da7dabfac484efe37a5380ee9088f7ace2efcde9
                          ^
```

In 2 seconds you see: "first byte differs — `b9` vs `b8`. Looks like a
single-bit corruption or off-by-one in their key derivation."

**Base64** (same situation):
```
expected: uU0nuZNNPgilLlLX2n2r+sSE7+N6U4DukIj3rOLvzek=
got:      uE0nuZNNPgilLlLX2n2r+sSE7+N6U4DukIj3rOLvzek=
           ^
```

Now you see: "second character differs — `U` vs `E`." But what does that
*mean*? You have to mentally reverse the base64 encoding to figure out
which byte that corresponds to. Same information, harder to interpret
without a calculator.

## Part 4: What "spot byte changes easily" actually buys you in production

It's not about cosmetics. It's about **how fast you can identify the
failure mode** when a partner stops verifying. Each minute you can't
diagnose is a minute the partner's traffic is broken. Here are the
scenarios where hex pays for itself.

### Scenario 1: The 2am page — partner signatures suddenly failing

**Setup:** PagerDuty wakes you up. Partner `acme-payments` has been
hitting `/events` for 6 months with zero issues. At 02:14 UTC their
signatures started failing. Their request volume just dropped to zero
successful requests. They're losing money every minute.

**What you have in the logs:**

```
[02:14:33] partner=acme-payments verify=FAIL
  expected_fingerprint: b94d27b9934d3e08a52e52d7da7dabfac484efe37a5380ee9088f7ace2efcde9
  presented_signature:  uU0nuZNNPgilLlLX2n2r+sSE7+N6U4DukIj3rOLvzek=
  computed_with_key:    b94d27b9934d3e08a52e52d7da7dabfac484efe37a5380ee9088f7ace2efcde9
```

The expected and computed match — so the gateway *thinks* it's using
the right key. But the signature still fails. Something on the partner
side changed.

**You ask the partner:** "Send me the SHA-256 of your secret as you
compute it locally."

They reply with:
```
B94D27B9934D3E08A52E52D7DA7DABFAC484EFE37A5380EE9088F7ACE2EFCDE9
```

**Hex world: you see it in 5 seconds.**

You glance at the two strings:

```
Yours: b94d27b9934d3e08a52e52d7da7dabfac484efe37a5380ee9088f7ace2efcde9
Mine:  B94D27B9934D3E08A52E52D7DA7DABFAC484EFE37A5380EE9088F7ACE2EFCDE9
```

Same characters, different case. Hex is case-insensitive — the bytes
are identical. **The key is fine.** Move on. Must be a clock skew or a
canonical-message issue. You check `withinSkew` next, find their NTP
drifted to +120s, fix the time sync. Resolved at 02:21. **Total: 7
minutes.**

**Base64 world: you're chasing ghosts.**

If the same hashes were stored as base64, the partner sends:

```
Yours: uU0nuZNNPgilLlLX2n2r+sSE7+N6U4DukIj3rOLvzek=
Mine:  UU0NUZNNPGILLLLX2N2R+SSE7+N6U4DUKIJ3ROLVZEK=
```

`U` and `u` are **different bytes** in base64 (`U`=20, `u`=46). To you
this looks like the partner is computing a completely different key.
You spend 30 minutes comparing decoded byte arrays, asking them to walk
through their key-derivation code, suspecting their HMAC library before
someone notices "wait, did you uppercase that somewhere?" By then
you've burned an hour and the partner is furious.

**Hex's case-insensitivity + visual byte alignment told you the answer
at a glance.**

### Scenario 2: Onboarding a new partner — copy-paste corruption

**Setup:** You're onboarding `globex-corp`. They send their
`SHA-256(secret)` over Slack. You paste it into the partner-admin UI.
Their first 100 requests fail.

**What you see in logs:**

```
[14:02:11] partner=globex-corp verify=FAIL
  stored_fingerprint:   b94d27b9934d3e08a52e52d7da7dabfac484efe37a5380ee9088f7ace2efcd e9
                                                                                       ^ space?
```

Wait — there's a space between `cd` and `e9`. Or is it a non-breaking
space? Slack mangles whitespace.

**Hex world: the anomaly is loud.** Hex strings are dense, fixed-width,
no whitespace expected. A stray character **stands out like a broken
tooth.** You count: 65 chars instead of 64. You strip whitespace,
retry, fixed.

```bash
$ echo "b94d27b9...cd e9" | tr -d '[:space:]' | wc -c
64
```

**Total: 3 minutes.**

**Base64 world: the anomaly hides.** Base64 already contains `+`, `/`,
`=`, mixed case, and visually-similar chars (`I` vs `l` vs `1`, `0` vs
`O`). A stray space, a smart quote, or a copy-paste replacement of `+`
with a Unicode `＋` (full-width plus) is much easier to miss.

The partner's hash works locally and fails on the gateway. You spend
an hour suspecting their code before someone diffs the bytes and finds
the invisible character.

### Scenario 3: Key rotation — confirming the swap actually happened

**Setup:** A partner is rotating their secret. You roll the key in the
DB. The verifier supports a grace window — old key and new key both
verify for 24 hours. You want to confirm in monitoring that the **new**
key is actually being used by the partner now.

**Your dashboard logs:**

```
[partner=acme] verified_with=current  fingerprint_prefix=b94d27b9
[partner=acme] verified_with=current  fingerprint_prefix=b94d27b9
[partner=acme] verified_with=current  fingerprint_prefix=b94d27b9
[partner=acme] verified_with=previous fingerprint_prefix=a1f309c4   ← still old key!
[partner=acme] verified_with=current  fingerprint_prefix=b94d27b9
```

**Hex world: 4-byte prefix is a meaningful identifier.** `b94d27b9` and
`a1f309c4` are visually distinct. You can scan a 1000-line log and
count how many requests still hit the old key. You can use `b94d27b9`
as a tag in Grafana, in alert names, in incident comms ("the b9-prefix
key"). The hex prefix becomes a **stable handle for the rotation
operation.**

```bash
$ grep "verified_with=previous" verify.log | wc -l
47
$ # 47 requests still using the old key — partner hasn't fully rolled out
```

**Base64 world: prefixes are unstable.** Hashes that differ in their
first byte often share their first base64 character because base64
encodes 3 bytes per 4 chars and the leading bits get mixed. Two
different keys might both start with `uU0n` if their first 3 bytes
happen to share certain bit patterns. You can't reliably "tag" a key
by its first 4-6 base64 chars.

### Scenario 4: Forensics — "did the DB get tampered with?"

**Setup:** Audit alert fires. Someone with DBA access touched the
`partner_secrets` table outside the rotation pipeline. Security wants
to know: which keys changed, and by how much?

You pull the audit log:

```
BEFORE: b94d27b9934d3e08a52e52d7da7dabfac484efe37a5380ee9088f7ace2efcde9
AFTER:  b94d27b9934d3e08a52e52d7da7dabfac484efe37a5380ee9088f7ace2efcde0
                                                                       ^
```

**Hex world: instant verdict.** One nibble (4 bits) different in the
last position. Possibilities: typo, single-bit flip during write,
intentional minimal modification to test if the audit catches it. You
file an incident, escalate to the DBA, and forensics has a clean
signal to investigate.

The exact-position visibility matters because **single-character
corruption looks completely different from "a different key was
substituted":**

```
Substituted entirely: 8c3a91d27e... ← totally different across all 64 chars
Corrupted in transit: b94d27b9...e0 ← identical except trailing char
```

You diagnose the failure mode from the diff pattern alone.

**Base64 world: ambiguous.**

```
BEFORE: uU0nuZNNPgilLlLX2n2r+sSE7+N6U4DukIj3rOLvzek=
AFTER:  uU0nuZNNPgilLlLX2n2r+sSE7+N6U4DukIj3rOLvzeg=
                                                  ^
```

Last few chars differ. Could be a 1-bit flip, could be a 4-byte
difference at the end of the underlying bytes — base64 padding
amplifies trailing-byte changes. You have to decode both to byte
arrays and `xor` them to know how many bytes actually differ. Extra
step in a forensics workflow that's already time-pressured.

### Scenario 5: Cross-environment debugging — "works in staging, fails in prod"

**Setup:** A new partner integration works in staging, fails in prod.
Same code on both sides. You pull the stored fingerprint from each:

```
staging: b94d27b9934d3e08a52e52d7da7dabfac484efe37a5380ee9088f7ace2efcde9
prod:    b94d27b9934d3e08a52e52d7da7dabfac484efe37a5380ee9088f7ace2efcde9
```

**Hex world: instant "yes, identical" or "no, byte X differs".** You
don't even need a tool. Two lines, same length, monospaced font. Your
eye does the diff in one second. They match → the issue isn't the key.
Move on.

If they didn't match, you'd see *exactly* which bytes drifted, which
often points at the cause:

- All 32 bytes different → wrong secret stored entirely
- First few bytes match, then diverge → wrong hash algorithm somewhere (SHA-256 vs SHA-512 truncated)
- Identical except for case → encoding pipeline diff
- Identical except trailing bytes → padding/truncation bug

Each diff pattern has a **signature failure mode**, and hex makes the
pattern visible.

**Base64 world: you reach for `diff`.** It says "they differ at column
47." You decode both, byte-compare, find they're actually identical
except one is base64url and one is standard base64 (one has `+/` and
the other has `-_`). Five extra minutes spent on a tooling artifact.

### The pattern across all five scenarios

The thing hex buys you isn't "prettier strings." It's **fast pattern
recognition under time pressure.** When something is broken in
production:

1. **You're tired or stressed.** Cognitive load matters.
2. **You don't have time to write a script.** You need answers from
   the screen in front of you.
3. **The diff *pattern* is itself diagnostic.** Single-byte corruption,
   case-folding, length mismatch, total substitution — each looks
   different in hex, and the look tells you the failure mode.
4. **Communication speed matters.** "The b9-prefix key" is something
   you can say in a Slack channel. "The uU-prefix key" is ambiguous
   and forgettable.

Base64 forces you through a decode/compare/decode loop for every
diagnostic question. Hex gives you the answer at a glance.

The size cost (64 vs 44 chars) is irrelevant for a stored value. The
diagnostic speed advantage compounds across every incident for the
lifetime of the system. Over years, that's hours of MTTR saved per
incident × hundreds of incidents.

### Production-task summary

| Production task | What hex gives you |
|---|---|
| **Triaging a 2am page** | Visual diff in seconds, no tooling needed |
| **Onboarding new partners** | Copy-paste corruption (whitespace, case) is loud |
| **Confirming key rotation** | Stable, memorable prefixes for tagging/searching |
| **Forensic audit** | Diff pattern reveals the failure mode (corruption vs substitution) |
| **Cross-environment debug** | Direct visual comparison; no decode step |

Hex isn't *more secure* than base64. It's **faster to read under
pressure.** That's the production payoff.


## TL;DR

- Hex and base64 are **not security choices** — both are reversible,
  both are public knowledge, neither hides anything.
- **Storage** optimizes for: human inspection, fixed width, tooling
  convention, debug ergonomics → **hex wins**.
- **Wire** optimizes for: byte count, machine handling, HTTP convention
  → **base64 wins**.
- Hex aligns 1 byte ↔ 2 chars at fixed positions. A one-byte change
  always shows up as a 2-char change in a predictable spot — perfect
  for eyeballing diffs in logs.
- Base64 packs 3 bytes into 4 chars, so byte boundaries don't align
  with character boundaries. A one-byte change can shift multiple chars
  in ways that obscure which byte actually changed.
- 32 bytes → 64 hex chars or 44 base64 chars. The 31% size penalty is
  worth paying for storage; not worth paying on every HTTP request.
