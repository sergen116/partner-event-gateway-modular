What solves the actual scaling bottleneck?

Partner Event Gateway — supplementary diagram. Five bottlenecks in the order they appear, with the right fix for each and what only looks like a fix.

Most "scaling" problems are misdiagnosed. Hourly partitioning solves a problem people think they have but rarely the one they actually have. Diagnose first; pick the lever the diagnosis names.

Four signals worth distinguishing

Before reaching for any lever, ask which of these symptoms you actually have. Each maps to a different fix; mixing them up wastes effort.

Signal 1

Queue depth grows unboundedly

Workers always busy. Adding polling does not help.

Diagnosis: consumer-side throughput problem.

Signal 2

Queue depth fine, latency high

Throughput keeps up with arrival rate, but per-message publish→processed time is high.

Diagnosis: consumer pickup latency.

Signal 3

API CPU spikes during bursts

Pod CPU pegged on ingest. p99 latency spikes. 503s under load.

Diagnosis: producer-side problem.

Signal 4

Postgres pegged regardless

CPU/IOPS saturated even when consumer count is low.

Diagnosis: database-tier problem.

What concurrent operation is bottlenecked, and what physical resource is it bottlenecked on? That single question routes you to the right layer.

Partitioning is for retention, not throughput

What partitioning solves

  • Cheap retention via DROP PARTITION instead of DELETE
  • Vacuum-free archive partitions (no churn on cold data)
  • Backup/restore granularity
  • Parallel scans on historical time-range queries

What partitioning does not solve

  • Hot-tail B-tree contention (writes still target one child)
  • Page-level lock saturation on the current partition
  • Per-tenant blast radius from a noisy neighbour
  • Single-queue throughput ceiling

Time partitioning splits the history of writes; partner sharding splits the concurrent stream of writes. Contention is a property of concurrency, not history.

Quick mental check

If your fix for "the queue is too slow" is "make smaller partitions," ask:

  • Are concurrent writes spread across more children, or concentrated on the latest one?
  • If concentrated → the contention point did not move
  • If spread → you are sharding, not partitioning, regardless of what you call it
